# Phase 5 diagnostic, manifest, runner, QA, and rights notes

**Prepared:** 2026-11-11
**Scope:** Independent implementation research for DIAG-01..03, VERIF-04, CPU-01..02.
**Status:** Code and planning documents inspected; no build, test, CI, toolchain install, or private-content access was performed.

## Phase scope and accepted constraints

The roadmap asks for project-authored ARM and Thumb diagnostics built from source with a pinned ARM toolchain, an owned startup/link/header path, no Nintendo logo bytes or linked runtime library, machine-readable mailbox verdicts, and deliberately broken variants. The requirements add full ARMv4T ARM/Thumb coverage and visible SKIPPED outcomes for missing tools or unmet BIOS requirements. The exact success criteria are in [ROADMAP.md](../../ROADMAP.md#L238) and [REQUIREMENTS.md](../../REQUIREMENTS.md#L33).

Use the current agb direct-start / BIOS-none contract. Do not use a retail game, Nintendo BIOS, third-party diagnostic suite, devkitARM, libgba, or gbafix. The owner’s project-license decision remains open; it does not authorize inventing a project-wide license. The standing rights limits and fixture-specific provenance rules are in [AGENTS.md](../../../AGENTS.md#L25) and [evidence-contract.md](../../../docs/evidence-contract.md#L9).

## Source facts

### CPU startup and diagnostic boundary

- The current reset path zeroes CPU state, then sets CPSR=0x000000DF and execution address 0x08000000 ([machine.c](../../../src/machine.c#L3-L27)). The Phase 4 context describes these as deterministic project defaults, not a BIOS handoff; general/banked registers and SP/LR start at zero, the pipeline is empty, and owned diagnostics establish any stack they need ([04-CONTEXT.md](../04-cpu-execution-core-and-headless-runner/04-CONTEXT.md#L32)).
- The public header defines mailbox address 0x03007FC0, magic 0x47424C4B, version 1, completion marker 0x434F4D50, and four mailbox state values ABSENT=0, RUNNING=1, PASS=2, FAIL=3 ([gamebloke.h](../../../include/gamebloke/gamebloke.h#L324-L336)). The mailbox is five little-endian words: magic, version, state, case ID, completion marker; the guest writes the marker last ([gamebloke.h](../../../include/gamebloke/gamebloke.h#L329-L330)).
- The reader returns a terminal verdict only for valid magic/version, a PASS or FAIL state, a nonzero case ID, and the completion marker. A partially written terminal mailbox remains pending, and a zero-filled mailbox is absent ([inspect.c](../../../src/inspect.c#L131-L181)).
- Runner status and mailbox semantics are separate. The result contract requires a completed PASS or FAIL mailbox to have a nonzero case ID; PASS also requires positive guest progress and mailbox-complete termination. The checker does not know the fixture’s expected case ID, so a diagnostic test must assert the exact ID itself ([evidence-contract.md](../../../docs/evidence-contract.md#L128)).
- The current profile version 4 lists an ARM/Thumb subset. It explicitly excludes ARM block transfers, multiply, full PSR transfers, Thumb BL pairs, and other supported-vs-unsupported forms needed by this phase ([agb.json](../../../profiles/agb.json#L92-L125)). Phase 4’s cpu_test vectors are valuable implementation context, but they are host tests and do not replace source-built guest diagnostics.

### Production manifest and runner admission

- tests/fixtures/manifest.json currently contains an empty fixtures array ([manifest.json](../../../tests/fixtures/manifest.json#L1-L4)). The production runner index is generated only from that canonical file; its separate control index is artificial and not a source of production authority ([GenerateFixtureIndex.cmake](../../../cmake/GenerateFixtureIndex.cmake#L3-L6), [evidence-contract.md](../../../docs/evidence-contract.md#L177)).
- A production run with a registered ID checks the loaded ROM’s SHA-256 against the immutable indexed digest before guest execution. A mismatch is refused before execution. Rows with a BIOS requirement other than none return SKIPPED before execution ([run.c](../../../runner/run.c#L398-L459)). Unregistered raw paths may expose mailbox observations but are classified GUEST_STOP with unregistered-content; they cannot validate as a manifest-backed PASS ([run.c](../../../runner/run.c#L299-L314), [evidence-contract.md](../../../docs/evidence-contract.md#L182)).
- The manifest row requires source, license/notices, build recipe/toolchain identity and digest, BIOS requirement, expected-value provenance, and permitted use. Source forms are git, url, and in-tree; git needs a 40-hex commit, while url and in-tree need SHA-256 ([CheckManifest.cmake](../../../cmake/CheckManifest.cmake#L20-L37)).
- GenerateFixtureIndex.cmake extracts its runtime ROM digest from the validated row SHA field. For in-tree, it resolves source.path under GBL_SOURCE_DIR and verifies the file bytes against source.sha256 before emitting the index ([GenerateFixtureIndex.cmake](../../../cmake/GenerateFixtureIndex.cmake#L168-L193), [GenerateFixtureIndex.cmake](../../../cmake/GenerateFixtureIndex.cmake#L231-L240)). A git row pins the source commit but has no byte digest in the current row/index contract; the producer refuses a registered row without a usable digest (fixture-digest-unavailable) ([run.c](../../../runner/run.c#L423-L438), [evidence-contract.md](../../../docs/evidence-contract.md#L118)).
- Thus build.recipe and the toolchain digest document how output is produced, but do not currently become the runner’s output-byte pin. A source-built fixture needs its generated ROM digest available to the production index before that runner can issue PASS.
- The present CMake fixture-generation edge is gbl_instruction_image → generated build-tree images → validated indexes → production/control runners. Existing images are native synthetic contract fixtures, not ARM diagnostics; their control rows explicitly use local-only, redistributable unknown, and a synthetic LicenseRef ([CMakeLists.txt](../../../CMakeLists.txt#L89-L170), [GenerateFixtureIndex.cmake](../../../cmake/GenerateFixtureIndex.cmake#L46-L113)). They must not be promoted into the production manifest.
- gamebloke.result/1 already carries fixture ID, actual ROM digest, status, semantic state/case ID, time, limits, disputes, and claim fields. Its checker enforces producer/status consistency and digest binding for in-tree and url rows; no new result field is needed just to test exact diagnostic case IDs ([CheckResult.cmake](../../../cmake/CheckResult.cmake#L364), [evidence-contract.md](../../../docs/evidence-contract.md#L95-L136)).

### CI, inventory, and negative-control behavior

- The required local/CI command is cmake --workflow --preset ci. CTest inventory must list each test; the JUnit post-step shows expected, ran, and skipped counts. gbl_add_test(SKIPPABLE) turns output containing SKIPPED: into a visible CTest skip, and inventory lines marked skip-ok permit only that reported skip ([GblTests.cmake](../../../cmake/GblTests.cmake#L7-L55), [docs/verify.md](../../../docs/verify.md#L12-L26)).
- The current ci preset uses build/ci; the ASan preset uses build/asan ([CMakePresets.json](../../../CMakePresets.json#L1-L75)). Both CI and ASan inventories are checked independently. A manifest path for generated binaries therefore must account for both build lanes or the build/index flow must deliberately keep the new external-toolchain diagnostics confined to the CI lane.
- The current hosted build, ASan, hygiene, and required-check jobs have three-minute timeouts. The build job currently runs the canonical CI preset without installing the ARM cross-toolchain; this phase must add a pinned-tool install/verification step and then run the same preset. Preserve the current time cap and measure the added critical path ([ci.yml](../../../.github/workflows/ci.yml#L92-L145)).
- The inventory already distinguishes host-side harness failures from guest outcomes through the closed nine-state result vocabulary. Keep guest assertion failure as GUEST_FAIL; malformed/unsupported/no-BIOS behavior as its existing stop/refusal reason; tool absence or unmet declared BIOS as SKIPPED; and build/setup/trace/checker failures as harness/CI failures. A host ASan/UBSan success establishes host C behavior only, not ARM guest instruction correctness ([evidence-contract.md](../../../docs/evidence-contract.md#L63-L92), [docs/verify.md](../../../docs/verify.md#L97-L131)).
- Keep the two skip surfaces distinct in the design: a missing local toolchain makes the CTest diagnostic test visibly SKIPPED in JUnit/inventory, while an indexed fixture whose BIOS requirement cannot be met emits a result JSON with status SKIPPED and ran=false. A negative diagnostic mailbox is a completed guest FAIL and runner GUEST_FAIL, not a skipped test, a no-BIOS GUEST_STOP, or a host HARNESS_FAIL ([GblTests.cmake](../../../cmake/GblTests.cmake#L43-L53), [run.c](../../../runner/run.c#L451-L459), [evidence-contract.md](../../../docs/evidence-contract.md#L63-L92)).
- The manifest checker permits public-ci only when license.redistributable is yes, and rejects a public-CI row that requires user-official BIOS ([CheckManifest.cmake](../../../cmake/CheckManifest.cmake#L425-L435)). The checker does not verify legal meaning or SPDX syntax of the license string; it requires a nonempty string and nonempty notices. Rights therefore need an honest fixture-specific notice, not just a digest or provenance label ([CheckManifest.cmake](../../../cmake/CheckManifest.cmake#L266-L302)).

### Rights scan and output handling

- ROM-like extensions, binary files, the known Nintendo-logo header window, and known BIOS digests are scanned by signature-scan.sh. The exact-path allowlist exempts only the extension/binary findings; it never exempts logo or BIOS digest detection ([signature-scan.sh](../../../scripts/signature-scan.sh#L12-L25), [signature-common.sh](../../../scripts/lib/signature-common.sh#L33-L80)).
- --tree sees tracked files and untracked non-ignored files. Project build outputs are ignored by /build*/ and *.gba, so a successful tree scan does not inspect generated diagnostic ROMs ([signature-scan.sh](../../../scripts/signature-scan.sh#L142-L159), [.gitignore](../../../.gitignore#L1-L15)). Use a separate narrow scan of the generated ROM directory with exact generated filenames in a temporary allowlist. That scan still applies known-logo-window and known-BIOS digest checks; do not add a broad build/ or *.gba allowlist to the repository file.
- Existing CI uploads JUnit only on failure. Do not add ROM artifacts or BIOS material to logs or uploads; diagnostics only need their machine-readable result and the gate summary ([ci.yml](../../../.github/workflows/ci.yml#L111-L120)).

## Planning recommendations

### 1. Keep the diagnostic executable self-contained

Use original assembly sources with a project-owned entry stub, linker script, and small header fixer. Place the entry branch at 0x08000000, establish an explicit guest stack because machine reset deliberately leaves SP unset, and reserve the mailbox range away from stack/data. Keep startup and mailbox instructions inside the supported instruction subset that is implemented first. No BIOS handoff, SDK runtime, helper library, or third-party content should be required.

Build separate ARM and Thumb diagnostic ROMs plus deliberately broken variants. Keep the ROM outputs under an ignored, deterministic project build path. The tests should run each through the production gamebloke-run --fixture <id> target. Do not route actual Phase 5 evidence through gamebloke-run-control or a second result producer.

### 2. Make case coverage and expected values reviewable

Maintain a compact machine-readable case matrix beside the diagnostics: stable nonzero uint32 case ID; ARM/Thumb state; instruction/operand edge; setup and observed register/flag/memory result; independently derived expected value and its primary source/derivation; positive fixture; negative fixture; expected mailbox state; and whether trace evidence is needed. The current result checker cannot enforce per-fixture expected case IDs, so the CTest gate must compare exact status, semantic state, and case ID from actual production CLI JSON.

Cover the entire promised ARMv4T ARM and Thumb instruction/operand matrix, not just the named corner cases. Assign explicit stable IDs to barrel-shifter carry, empty-list/base-in-list/user-bank LDM/STM, misaligned-load rotation, multiply flags, PSR transfers, and Thumb BL prefix/suffix. For BL, prove two separately observed instruction records/addresses and the resulting link/return behavior. Derive expected outputs from the ARM7TDMI primary documentation or transparent arithmetic; do not use Gamebloke’s own implementation as its oracle or another emulator’s passing result as accuracy evidence.

Because the profile currently publishes an explicit supported/excluded opcode scope, completing that scope changes a profile-bearing CPU claim. Bump profile version 4 to 5 only for that claim change and synchronize profiles/agb.json, docs/profile-agb.md, CheckProfile.cmake, and profile controls. Do not bump the profile just for linker/toolchain mechanics that do not change the claim. Phase 4 records this synchronization rule ([04-CONTEXT.md](../04-cpu-execution-core-and-headless-runner/04-CONTEXT.md#L42)).

Each negative variant must run the same real instruction sequence and assertion as its positive counterpart, then fail at a named assertion with the same fixed case ID. Avoid a branch that directly writes FAIL, a dead block, a fabricated mailbox, or a skip path masquerading as a CPU test. Be explicit that the broken variant validates diagnostic failure plumbing; it is not a hardware measurement or independent proof that the emulator implementation is correct.

### 3. Resolve output-byte admission without changing result/1

The existing admission path requires a committed SHA-256 for the exact generated ROM bytes before production-runner PASS. Do not pin that digest until the separate toolchain spike has positively established Tag_CPU_arch: v4T and attempted byte-for-byte macOS/Linux reproducibility, as required by the roadmap.

Preferred minimal path: first build unregistered diagnostic outputs in an ignored build location on both hosts; record the architecture attribute, exact build recipe/toolchain identity, and byte comparisons; then add production manifest rows containing the proven ROM digest and wire the same deterministic build outputs ahead of fixture-index generation. One workable use of the current schema is an in-tree row whose path resolves to a stable ignored ROM output under the repository build tree and whose source.sha256 is that ROM’s digest; build.recipe must name every tracked assembly/startup/linker/header input and the pinned toolchain. Preserve exact source revision in the recipe/build provenance or use a separate source-commit pin if the row model can do that without self-referencing the commit that contains the row.

Before plan lock-in, explicitly choose the manifest/output path seam: current in-tree digest semantics bind one file (the ROM), whereas a git row binds one commit but cannot supply the runner’s expected ROM digest. Do not silently treat the source assembly digest as the output ROM digest. If the build-path workaround is too lane-specific or unclear, add an explicit build-artifact SHA field with backward compatibility for existing manifest/1 rows; keep gamebloke.result/1 unchanged. Avoid a schema/result version change unless semantics or fields actually change.

If macOS and Linux bytes differ, follow the roadmap’s Linux digest-ownership fallback and state clearly which exact fixture bytes CI runs on each platform. Do not claim one cross-host digest or let macOS output pass a Linux-pinned row without an explicit, validated platform-specific identity. A git self-reference to the commit containing its own row is circular; a source-only commit followed by a digest-bearing admission commit avoids that cycle.

### 4. Wire skips and controls so CI cannot go green without diagnostics

- Add the pinned toolchain installation and identity check to the existing CI build job before cmake --workflow --preset ci; required CI must configure with diagnostics mandatory. Missing installation or an unusable/mismatched toolchain in required CI is a build/setup failure, never a CTest skip.
- In local runs without the toolchain, have the registered diagnostic test report SKIPPED: <specific missing dependency/reason> and use SKIPPABLE plus skip-ok in the corresponding inventory. When toolchain is found but compilation or execution fails, fail the test; do not convert arbitrary command errors into skips.
- Keep a negative control that simulates the missing-toolchain branch and asserts the exact visible SKIPPED reason, while the normal CI path asserts the pinned tool is present and the real guest tests execute. Ensure a skipped CTest cannot satisfy the mandatory CI guard.
- No BIOS is required by this phase’s direct-start fixtures; their manifest rows should declare bios_requirement: none. Preserve the runner’s explicit SKIPPED response for any fixture row that declares an unavailable BIOS, and retain/extend a producer control that proves it is ran:false, has the reason, and never becomes PASS. Do not invent a BIOS fallback.
- Add build outputs → production index → runner/test dependencies explicitly. Register the diagnostic producer tests in tests/inventory/ci.txt (and ASan inventory only if that lane must build/use those assets), then update docs. The case gate should feed actual production CLI JSON into CheckResult.cmake and separately assert exact case IDs/outcomes.
- Scan generated ROM outputs with a dedicated, path-exact allowlist for the expected output names. Add a link-map gate that rejects any linked C runtime/library or toolchain CRT/startup objects; the only startup code should be the project-owned stub. Preserve the normal source-tree rights scan and all existing signature controls.
- Keep tests bounded and cheap enough for the existing three-minute hosted jobs; measure the added configure/build/test critical path and remove duplicate setup/build work before proposing any timeout or concurrency change.

### 5. Encode rights narrowly

Mark the source-owned rows project-authored only for expected values actually authored and independently documented by Gamebloke; use disputed with an existing dispute when an expected value is unresolved. Do not use hardware-observed without console measurements or reference-emulator as an oracle.

For public CI, permitted_use must include public-ci and the current checker requires license.redistributable: yes. Since this phase is limited to owner-controlled original source, record a fixture-scoped LicenseRef-Gamebloke-... plus a notice that limits the authorized use to this diagnostic in Gamebloke’s public CI, with no third-party assets and no project-wide license implication. The manifest fields record the owner’s scope; they do not create that permission by themselves. Do not label it MIT by copying another portfolio project, do not create a repository LICENSE, and do not treat project-authored provenance or the output digest alone as rights authorization. Keep each diagnostic’s recipe, source revision, toolchain digest, output digest, BIOS need, expected provenance, and allowed use in its row.

## Phase 4 limits to carry forward

- Phase 4’s verification says the runner/CPU requirements passed for the implementation slice; full ARM/Thumb coverage and BIOS execution were explicitly out of scope ([04-VERIFICATION.md](../04-cpu-execution-core-and-headless-runner/04-VERIFICATION.md#L92), [04-VERIFICATION.md](../04-cpu-execution-core-and-headless-runner/04-VERIFICATION.md#L106)).
- The production manifest stayed empty and synthetic control rows do not grant fixture rights ([04-VERIFICATION.md](../04-cpu-execution-core-and-headless-runner/04-VERIFICATION.md#L132), [04-VERIFICATION.md](../04-cpu-execution-core-and-headless-runner/04-VERIFICATION.md#L191)).
- All 11 Phase 4 taxonomy probe rows remain unresolved in its report; new CPU diagnostic coverage should cite its own assertion/evidence and must not relabel those historical taxonomy items as resolved ([04-VERIFICATION.md](../04-cpu-execution-core-and-headless-runner/04-VERIFICATION.md#L213)).
- The current profile and runner still disclaim BIOS behavior, timing qualification, peripherals, and broad game compatibility. Phase 5 diagnostics can establish named CPU behaviors under the project’s direct-start policy; they do not establish post-BIOS behavior, physical hardware accuracy, general game compatibility, or public release readiness ([evidence-contract.md](../../../docs/evidence-contract.md#L205)).

## Unknowns for planning

1. **Manifest/generated-output representation:** Prefer a stable ignored in-repository build output path with the existing in-tree digest field if it remains portable across CI presets. Otherwise add an explicit output digest field while preserving old result documents. This is the main integration seam to resolve before slicing plans.
2. **Cross-host mismatch behavior:** The roadmap says Linux owns the digest if the macOS/Linux byte comparison fails, but the exact macOS runner/manifest identity under that branch is not stated. Resolve in the toolchain spike plan; never infer cross-host equality.
3. **Public-CI permission wording:** The manifest has fields to record a narrow fixture-level grant but does not validate legal terms. The row must record the owner-authorized scope for the project-authored fixture without implying a project-wide license.
4. **ASan lane participation:** Current ASan build creates runner/index targets from the same manifest. If the new toolchain is installed only in the canonical CI build job, decide whether diagnostics are also generated in ASan, moved behind a CI-only target, or share a stable generated path without weakening the canonical production-runner tests.
