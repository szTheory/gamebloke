## Fixed Findings

### CR-01: Store writeback alias is refused

**Files modified:** `src/cpu.c`, `tests/cpu_test.c`  
**Commit:** `8213adb`  
**Applied fix:** The single-transfer decoder now refuses any writeback transfer where `Rd == Rn`, before creating data slots or register effects. Replaced the positive post-indexed `STR r0, [r0], #4` oracle with legal no-writeback STR and STRB alias companions. Added atomic refusal coverage for pre-indexed and post-indexed STR and STRB aliases. The refusal helper checks canonical machine contents, machine identity, trace metadata, and trace-record bytes.

**Architecture evidence:** Cached ARM DDI0100I A4.1.99 says STR writeback with `Rd == Rn` is UNPREDICTABLE; A4.1.100 says the same for STRB. ARM7TDMI DDI0029G §§6.7–6.8 describe generic load/store cycle behavior and do not specify a same-register store exception. No exact-core behavior was inferred from the generic timing tables.

**Negative control:** Before the source guard, the four new pre/post word/byte alias cases failed while legal companions passed. Output: `build/phase05-plan10/review-fix/cr01-red.log`.

### CR-02: STRB with PC source is refused

**Files modified:** `src/cpu.c`, `tests/cpu_test.c`  
**Commit:** `4c5ed7c`  
**Applied fix:** Byte transfers with `Rd == R15` now use the existing unpredictable-instruction refusal path for both load and store. Added an atomic STRB-PC source refusal alongside the retained LDRB-PC refusal.

**Architecture evidence:** ARM DDI0100I A4.1.100 marks R15 as an UNPREDICTABLE STRB source. The generic ARM7TDMI §6.8 store-cycle description does not define a special STRB-PC outcome.

**Negative control:** Before broadening the guard, the new STRB-PC assertion was the only failing transfer assertion. Output: `build/phase05-plan10/review-fix/cr02-red.log`.

### WR-01: Modulo LDR-PC refill pair has an explicit next-run boundary result

**Files modified:** `src/cpu.c`, `tests/cpu_test.c`  
**Commit:** `99d036a`  
**Applied fix:** Pipeline validation now accepts the exact ARM `0xFFFFFFFC` then `0x00000000` pair generated by the approved modulo-32 LDR-PC refill policy. On the next run, decode returns the existing unpredictable-unit result before executing the boundary instruction. The existing core mapping stops with `GBL_CPU_STOP_UNSUPPORTED_INSTRUCTION` / `GBL_RUN_REASON_UNSUPPORTED_INSTRUCTION`; no public result schema or unpredictable classification was added. The second-run test checks zero additional cycles/instructions and unchanged canonical state, instance identity, and refill trace bytes apart from the stop fields.

**Architecture evidence and limit:** ARM DDI0100I A2.7.1 says normal ARM sequential execution from `0xFFFFFFFC` to `0` is UNPREDICTABLE, and distinguishes prefetch from executing the boundary instruction. The test preserves the already-approved modulo refill, then records this emulator's explicit stop policy before the next instruction has effects. This is not a hardware-accuracy claim. The static B/BX refill guards were left unchanged.

**Negative control:** Before the pipeline fix, the second `gbl_cpu_run` failed the boundary assertion because checked address addition returned generic invalid CPU state. Output: `build/phase05-plan10/review-fix/wr01-red.log`.
