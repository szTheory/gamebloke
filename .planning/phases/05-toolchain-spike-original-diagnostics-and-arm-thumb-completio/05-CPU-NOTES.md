# Phase 5 CPU Research Notes

**Prepared:** 2026-11-11
**Scope:** Full ARM7TDMI ARMv4T ARM and Thumb completion, CPU-specific architectural quirks, and the interpreter/preflight seam. Supporting research for Phase 5 discussion and planning; not canonical RESEARCH.md or CONTEXT.md. No source changes or test runs were made.

## Recommendation

Complete the exact ARM7TDMI ARMv4T instruction set through the existing single interpreter. First make the decoded instruction unit able to represent every fetch, data transaction, register write, status update, and internal cycle needed by that one instruction. Preflight and execution must consume that same plan. Then complete the ARM families, status and banked-register behavior, and every Thumb format, while recording each architecture-defined quirk in the owned diagnostic mailbox by stable case ID.

The present unit is deliberately smaller than the required ISA: it holds at most two fetch descriptions, one data access and three staged trace records. A 16-register LDM/STM that loads PC can require 16 memory records, a two-fetch refill, and one instruction record. SWP has both a read and a write. Grow the same-unit plan and its capacity/preflight rules; do not add a second decoder, timing predictor, or fused instruction path. This follows the accepted Phase 4 whole-unit preflight and single-interpreter constraints. Preserve the current direct-start, no-BIOS profile and its explicitly unqualified bus timing. Complete CPU semantics do not bring in BIOS/HLE, timers, DMA, active device IRQ scheduling, Game Pak wait states/prefetch, or host clocks. Describe outputs as tests of defined ARMv4T behavior plus explicit project policies for architecturally unpredictable results—not as hardware qualification. ## Current implementation seam

Phase 4 intentionally supports a bounded subset. The current profile lists ARM MOV/ADD/SUB/CMP/AND/ORR, B/BL/BX, pre-indexed immediate byte/word transfers, and a small Thumb subset; valid but unsupported instructions stop separately from reserved undefined instructions. Preserve that honesty while adding support. [VERIFIED: docs/profile-agb.md, “CPU instruction scope”; verbatim: “ARM data processing: MOV, ADD, SUB, CMP, AND, ORR”; “ARM control flow: B, BL, BX”; “ARM single transfer: LDR/STR byte or word, immediate 12-bit offset, pre-indexed, no writeback”; “All other valid-but-unimplemented opcodes and operands stop as unsupported, reserved undefined encodings remain distinct”.]

The CPU implementation already centralizes condition evaluation, register banking, branch/refill, exception entry and bus use. But its current unit shape represents one read-or-write transfer, and trace capacity is fixed at three. Its R15 helper returns the common +8/+4 value without an operand-use parameter; data-processing decode currently rejects PC destinations and register shifter reads of PC. These are expansion seams, not reasons to fork execution. UINT32_C(4) : UINT32_C(8));”; “static bool gbl_cpu_condition_passed”.]

The public CPU exception API can inject an exception boundary between two calls to run. That is enough to test Thumb BL prefix state, inject IRQ after the prefix, and inspect architected mode/LR/SPSR state with BIOS absent. It does not require an active interrupt controller or promise guest IRQ-handler execution. ## Architectural facts and explicit project policy

### Defined arithmetic, conditions, and shifts

- Use unsigned bit-vector arithmetic for all 32-bit operations. ADC/SBC/RSC must compute carry-in/out and signed overflow without C signed overflow; long multiplication must produce the exact 64-bit architectural result without an out-of-range unsigned-to-signed cast. Reuse the existing helpers where their semantics fit, and add narrowly scoped arithmetic helpers rather than C-shift shortcuts. The project’s UBSan lane is useful enforcement, but passing it does not prove the vectors cover all boundaries. [VERIFIED: src/cpu_helpers.h:10-19, 27-131; verbatim: “typedef struct gbl_shift_result”; “typedef struct gbl_arithmetic_result”; “static inline gbl_shift_result gbl_shift”; “static inline gbl_arithmetic_result gbl_add_flags”.]
- For ARM immediate Operand2, a zero rotation preserves old C; a nonzero even rotation sets C from the rotated result. For immediate shifts, LSL #0 preserves carry, LSR/ASR #0 mean 32, and ROR #0 is RRX through old C. For register shifts, use Rs low 8 bits; count 0 preserves operand and C; define 1–31, 32, >32, and ROR multiples of 32 exactly. Register-specified shifts have an extra internal cycle in the ARM7TDMI timing tables. [CITED: [ARM Architecture Reference Manual DDI0100I, A5.1–A5.2, A4 data-processing semantics](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a); [ARM7TDMI TRM DDI0029G, §6.5–6.6](https://documentation-service.arm.com/static/5e8e1323fd977155116a3129).]
- Logical/test operations that set flags update N/Z/C (shifter carry), preserve V; arithmetic/test comparisons update N/Z/C/V per arithmetic result. ADC/SBC/RSC use incoming CPSR.C. Failed conditions retire as a no-effect instruction while retaining expected sequential fetch/cost policy. [CITED: [ARM Architecture Reference Manual DDI0100I, A3.2–A3.3 and A4 instruction operation pages](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a).]

### PC and state transitions

- General visible PC is current instruction address +8 in ARM and +4 in Thumb; Thumb PC-relative address formation is word aligned. Instruction-specific PC reads override the base rule. ARM STR with R15 source observes current+12. Register-shifted data-processing Operand2 reading R15 also has the +12 case; thread that as an explicit operand-read context rather than changing every PC read. [CITED: [ARM7TDMI TRM DDI0029G, ARM/Thumb programmer’s model and §6 instruction timing](https://documentation-service.arm.com/static/5e8e1323fd977155116a3129); [GBATEK 3.06, Using R15](https://mgba-emu.github.io/gbatek/#arm-opcodes-data-processing-alu).]
- On ARMv4T, LDR PC does not interwork; LDM loading PC without S does not set T. BX selects T from bit 0. S-bit data-processing-to-PC and LDM^ with PC restore CPSR from the active mode’s SPSR. Thumb POP PC has the ARMv4 behavior; do not import ARMv5+ interworking rules. ARM target alignment requirements and cases specified as unpredictable need their own class/policy. [CITED: [ARM Architecture Reference Manual DDI0100I, A2.3, A4 LDM/data processing/BX entries](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a); [GBATEK 3.06, ARM state changes, LDM/STM, and Thumb POP](https://mgba-emu.github.io/gbatek/#arm-cpu-reference).]

### Transfers, alignment, and block edge cases

- Support each defined P/U/B/W/L and offset form; register offsets use the single-transfer shift rules and post-indexing writes back. The T form is privileged/user-bank translation for post-indexed ARM transfers. Preserve exact-core restrictions for PC and invalid destination/base combinations; do not accept an encoding simply because it has a plausible address. [CITED: [ARM7TDMI TRM DDI0029G, Table 1-3, pp. 1-13–1-15](https://documentation-service.arm.com/static/5e8e1323fd977155116a3129); [ARM Architecture Reference Manual DDI0100I, A5.2–A5.4](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a).]
- On the GBA policy/reference path, misaligned word LDR rotates the aligned word by 8×address-low-bits; odd LDRH rotates the aligned halfword by 8; odd LDRSH behaves like signed-byte load. Store addresses align down. The bus decides what raw width/value a region returns; CPU postprocessing must not silently assume every region is a 32-bit RAM cell. SWP word-read rotation and its write alignment require their own pinned case. These are documented emulator reference rules, not newly measured Game Boy Advance hardware. [CITED: [GBATEK 3.06, ARM CPU Memory Alignments and SWP](https://mgba-emu.github.io/gbatek/#arm-cpu-memory-alignments).]
- LDM/STM have four address modes, transfer registers in ascending register-number / ascending memory order, and apply mode-dependent start/final addresses. Under ARMv4, empty list acts through PC and base changes by ±0x40. STM with base in list stores old base only when base is first, otherwise final/new base; LDM with base in list does not write base back. S=1 without PC transfers user bank; LDM S=1 with PC restores CPSR. Thumb PUSH/POP are fixed SP stack modes, and Thumb LDM/STM are IA. Keep ARM empty/base-list rules distinct from Thumb rules where the source distinguishes them. [CITED: [GBATEK 3.06, ARM LDM/STM “Strange Effects on Invalid Rlist’s” and S-bit rules](https://mgba-emu.github.io/gbatek/#arm-opcodes-memory-block-data-transfer-ldm-stm); [ARM Architecture Reference Manual DDI0100I, A4.1.34–A4.1.35](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a).]

### Multiply and status register edge cases

- MUL/MLA S forms define N and Z from the low-word result and leave V unchanged; C is architecturally UNPREDICTABLE on ARMv4 and earlier. Long S forms define N/Z from the 64-bit result; both C and V are UNPREDICTABLE on ARMv4 and earlier. A deterministic profile policy (recommended: preserve pre-instruction C for short multiply and C/V for long multiply) is a project choice. Tests may assert defined bits and the chosen preservation policy, but the report must label the latter as project behavior, not physical accuracy. If a different policy is preferred for deterministic simplicity, document and pin it before diagnostics freeze. [CITED: [ARM Architecture Reference Manual DDI0100I, A4.1.34 MLA (A4-66), A4.1.40 MUL (A4-80), A4.1.88 SMULL (A4-168–169), and A4.1.129 UMULL (A4-251–252)](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a); [ARM7TDMI TRM DDI0029G, Table 1-2 and §6.6, pp. 1-12, 6-9–6-10](https://documentation-service.arm.com/static/5e8e1323fd977155116a3129).]
- The TRM describes multiplier early termination and variable internal cycles for MUL/MLA and all long forms. If CPU unit time includes these core-local internal cycles, compute them from the exact source operand during decode, store the result on the unit, and preflight it. This does not model Game Pak fetch waits or bus prefetch. If the accepted profile intentionally retains its current one-cycle bus placeholder without multiplier timing, state that limitation in the profile and case result; do not call timing fully ARM7TDMI-accurate. [CITED: [ARM7TDMI TRM DDI0029G, §6.6 and Tables 6-5–6-8](https://documentation-service.arm.com/static/5e8e1323fd977155116a3129).]
- MRS/MSR register and rotated-immediate forms need field-mask behavior and mode checks. User mode may write flags only; privileged writes can update allowed status/control fields; invalid mode values or setting T via MSR are architecturally unpredictable. User/System have no SPSR. R15 with S=1 exception-return forms are unpredictable without an SPSR. Keep N/Z/C/V changes and control/bank switch effects distinct. [CITED: [ARM Architecture Reference Manual DDI0100I, A2.5 and A4 MRS/MSR entries](https://documentation-service.arm.com/static/5f8dacc8f86e16515cdb865a).]

## Same-unit preflight and execution invariants

Plan this as an expansion of the decoded unit, not a speculative estimate. Load-to-PC (including LDM/POP PC and return-from-exception forms) makes the refill target unknown until an ordered bus read returns its value. SWP has a read-result dependency too: its old value feeds Rd while its write payload comes from the pre-instruction source register. The current source cannot express either dependency because every fetch address is fixed during decode and each unit has only one read-or-write transfer. The remedy is a symbolic same-unit plan, not an effectful read during preflight and not a second interpreter:

1. Decode once from the actual pipeline entry and capture every input read that may change meaning because of writes (store source values, starting base, mode/bank view, incoming flags, old CPSR/SPSR) before mutation.
2. Represent ordered instruction-fetch and data-transaction slots in bounded per-unit arrays. A slot may contain either a concrete decoded address or a pure address expression such as “branch target from result slot 0, plus fetch index × width”; the expression is resolved from an earlier transaction result during execution. Similarly, a read result may feed a planned register write, and a planned write payload may be snapshotted from the original register bank. SWP is two ordered data slots; LDM/STM is one slot per listed register (or the ARMv4 empty-list behavior); branch/refill slots remain part of the same unit.
3. Keep the dependency graph acyclic and explicit: decode computes addressing modes, static effective addresses, widths, transfer count/order, original source snapshots, target register-bank destinations and instruction semantics. Preflight does not access bus data. It validates every concrete data-address span, fetch/transfer counts, static alignment rules, retirement/master-clock overflow, and the complete resource envelope. Ordinary effective-address arithmetic is modulo 2^32, so do not reuse the current checked address-add helper where it would reject a defined wrapped data address; still validate each individual bus width/span before effects. For dynamic PC refill slots, determine target instruction state from the instruction (BX bit 0, or captured SPSR.T for exception return; ordinary LDR/POP PC does not interwork on ARMv4T), then apply the instruction’s PC alignment rule. ARM DDI0100I says sequential instruction overflow at the top of the address space is UNPREDICTABLE and software must not rely on wrapping to zero. Therefore freeze an explicit deterministic project policy for this already-reserved refill edge; recommended policy is 32-bit wrap to zero, labeled as policy for this unpredictable boundary. For an unpredictable loaded-PC alignment, also choose a deterministic policy (recommended: clear low alignment bits for the resulting ARM/Thumb state) so a post-read resolver cannot refuse the unit. No fetch outcome or target value is guessed. [CITED: ARM DDI0100I, A2.3 “Memory bounds”, lines 2799–2809; A2.3 PC-write alignment, lines 1772–1777.]
4. Under this profile, each bus transaction is one cycle, so the exact fetch/data count plus decoded internal cycles gives the exact preflight cost even when a refill address is dynamic. Check that cost against the remaining budget and machine-clock overflow before the first effect. In another profile with address-dependent bus costs, a dynamic target means exact cost cannot be known before reading it; that profile must provide a side-effect-free cost/transaction-planning contract or stop extending the same atomicity promise.
5. Preflight trace capacity for every planned slot before effects. For instruction tracing plus bus tracing, a maximum 16-transfer LDM/STM loading PC can require 19 records: 1 instruction + 16 data + 2 branch-refill fetches. SWP requires 1 instruction + 2 data + its planned fetch/refill. Reserve sequence-number headroom too. Trace records are populated with observed values and resolved addresses as slots execute, then committed only after the entire unit has completed.
6. Execute the stored plan in order, route every transaction through the existing bus API, use returned bus observations for trace, then commit register/CPSR/banked-state/refill effects in specified instruction order. Loads into R8-R14 must retain the intended bank from decode even when an SPSR return changes mode; for LDM^ PC, capture the current SPSR before transfer, load listed non-PC registers to the current mode’s bank, restore CPSR from that captured value, and use restored T to resolve the two already-reserved refill slots. For LDM^ without PC, send listed registers to the user bank and do not restore CPSR. Loads of PC are resolved after their data slot and determine the already-reserved refill slots. No handler re-decodes addressing or recomputes a different transfer list.
7. If the entire unit cannot fit the cycle budget, output trace buffer, sequence counter or machine counter, perform none of its instruction effects and leave trace untouched. Current `gbl_cpu_preflight` checks the aggregate exact cycle cost against budget and master-clock headroom, validates each planned fetch with `gbl_cpu_fetch_address_valid` (alignment and width span) and each concrete data operation with `gbl_cpu_data_span_valid`; the completed plan must likewise guarantee that every resolved dynamic refill address satisfies those rules before its fetch slot runs. The trace preflight reserves all records and sequence values, while records remain in a local staging array until commit. The current bus validates machine state, width, access class, address span and master-clock overflow before touching memory/open-bus/time; after those conditions pass, reads and writes return OK even for BIOS-absent, ROM-tail, unmapped and unimplemented-I/O addresses (those are outcomes, not checked-request failures). Aggregate preflight plus the fixed one-cycle bus contract therefore makes checked-request failures after the first transaction unreachable; do not depend on rollback for normal correctness. If future MMIO adds read side effects, arbitration, dynamic wait costs or post-preflight transaction failures, extend the bus with a prepare/commit or staged-transaction contract (or explicitly model the architecture’s partial-abort semantics) before adding that device. Never probe a status/data register during CPU preflight or invent a second machine snapshot/rollback engine. Phase 5 must not add WAITCNT, prefetch, active DMA/device concurrency or independent host time. ## Suggested tracer slices

These are implementation slices for planning, not architectural subsets to permanently declare complete:

1. **Plan-and-trace capacity seam.** Refactor the existing ephemeral unit to bounded fetch/transfer/register-effect arrays; preserve current behavior and whole-unit refusal guarantees. Prove trace exhaustion and cycle-budget refusal leave state, memory, time, and trace unchanged. Keep arrays bounded at architecture maxima and use checked counts.
2. **Complete ARM operand and ALU semantics.** Finish the 16 opcodes, immediate/register shifts, carry-in helpers, conditions, exact PC contexts, and S+PC exception-return path. Add semantic vectors and CPU-2/3/8 diagnostics; arithmetic-only units do not expand bus/device scope.
3. **ARM multiply, SWP and halfword transfers.** Add MUL/MLA/long forms and their status/cost policy, SWP/SWPB dual accesses, and all halfword/signed forms. Add CPU-5/6 vectors before trusting mixed block tests.
4. **ARM single-transfer/address mode matrix.** Complete immediate/register shifted offsets, U/P/W/L/B and post-index user-transfer forms. Verify read/write trace ordering, base writeback, forced alignment, PC restrictions and no-effects refusal. Make profile rows complete at this point.
5. **ARM/Thumb block and stack transfers.** Add per-register transfer list planning, user-bank/exception-return effects, all ARM modes and Thumb formats, empty-list/base-in-list cases, and dynamic trace/cost bounds. This is the highest preflight-risk slice; its maximum-work unit must be an explicit negative-control target.
6. **Thumb format completion.** Implement remaining immediate/register ALU operations, high-register forms, signed/halfword/register-offset and SP-relative/address forms, SP adjust, stack/multiple, and two-half BL. Add format ledger and CPU-7.
7. **Classification, CPU-1–9 diagnostics, and contract sync.** Audit all decoder regions against ARMv4T; expose the valid-unsupported / UND / unpredictable / extension / absent-coprocessor distinctions; fix condition=1111 routing; correct CPU-9 source note; update profile support/exclusion narrative, validators, original fixtures and manifest. Verify every positive and mutation case through the runner/mailbox with explicit limits.

The phase also owns the pinned toolchain and project-authored image build per DIAG-01/02. Keep those build concerns parallelizable from the core work only if they do not obscure that each case uses the same runner, case IDs, machine profile and source provenance.
