## Headless runner contract and host boundary

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Manifest-backed CLI over a caller-owned bounded CPU run API | Fresh state and explicit cycle/frame limits; `peek` can read mailbox without changing bus time/latch; fixture row supplies id, provenance, and dispute; bare ROM path cannot claim `PASS`. Fits [the C17 machine boundary](../../../include/gamebloke/gamebloke.h#L129) and [manifest/result contracts](../../../cmake/CheckManifest.cmake#L20). | Needs a bounded manifest-reading and general ROM-hash path in the C runner; instruction-boundary runs may cross a cycle limit; JSON and file errors need stable handling. | Core/API, runner, validator, install rules; risk: parser/hash bugs and contract drift. | Rec if runner JSON is evidence-bearing. |
| Harness resolves fixture metadata and invokes installed runner | Keeps JSON parsing outside core; existing CMake checks can validate ids, provenance, digest, and disputes; small C executable. | Runner cannot prove caller metadata was read from a manifest; raw calls can print claims rejected only later; runtime use of CMake/source paths breaks relocation. | Harness, runner, validator; risk: split-brain results. | Rec if raw runs stay diagnostic-only and cannot emit accepted `PASS`. |
| Raw-ROM debug output plus separate evidence composer | Easiest for CPU/mailbox debugging before owned diagnostics; no manifest parser in the CLI. | Two producers can diverge; raw output lacks required manifest identity/evidence; easy to mistake a mailbox word or hash for qualification. | Runner, composer, orchestration; risk: invalid output treated as evidence. | Rec only for a temporary debug mode that never emits `PASS`. |

**Rationale:** The repo already fixes the nine-state `gamebloke.result/1` vocabulary, requires fixture/evidence identity and dispute disclosure, and leaves semantic/time fields for Phase 4 ([vocabulary](../../../contracts/evidence.json#L6), [validator](../../../cmake/CheckResult.cmake#L20), [RUN requirements](../../REQUIREMENTS.md#L59), [roadmap](../../ROADMAP.md#L181)). Prefer the manifest-backed path: fresh machine state, explicit cycle/frame bounds, a read-only IWRAM `peek`, and a result derived from the supplied fixture row plus the digest of loaded bytes. Keep this dependency-free in C17; whether the runner parses the manifest or receives a verifiable row is the main implementation seam. Keep the status vocabulary closed: trace exhaustion stops without overwriting records and reports `HARNESS_FAIL` with reason `trace-output-full`; semantic result and actual cycles remain separate, and incomplete traces cannot overall `PASS`. Reject invalid metadata before execution, let a guest verdict beat a coincident budget check, then classify an exhausted bound as `TIMEOUT`; frame conversion and cycle arithmetic must be checked. Use a versioned mailbox with a magic value so zero-filled IWRAM cannot look like a verdict. Fresh loads reset CPU and bus state; refusal/allocation failure preserve existing state and input ([loader contract](../../../src/loader.c#L79), [Phase 3 context](../03-bus-api-memory-map-and-rom-loading/03-CONTEXT.md)). Bound reads by the existing ROM limit, escape JSON strings, validate digests, and omit machine-local paths. Install to a relative `bin` destination and use explicit runtime paths, with no CMake/source-tree dependency; this follows [CMake’s relocatable install guidance](https://cmake.org/cmake/help/v3.25/command/install.html#common-options). Minimum evidence: one synthetic manifest-backed positive run, unchanged state/time across `peek`, and moved-prefix output equality; negative controls for bare/unregistered input, digest/length errors, one-record-short trace, and allocation/refusal postconditions. These are routine implementation choices within the current contract. Owner input is only needed to add a new status/schema, allow unregistered ROMs to claim `PASS`, or require strict mid-instruction cycle preemption. Planning unknowns: exact mailbox layout and whether a cycle cap may stop at instruction boundaries with reported overshoot. Hardware facts remain with the separate ARM/TRM research.
