## Decision-relevant source observations

| Topic | Source observation | Planning consequence |
|---|---|---|
| ARMv4T scope | GBATEK's ARM CPU Versions section distinguishes ARM7/ARMv4 and Thumb-capable ARMv4T from later ARMv5/ARMv6 additions. The chapter also contains later ARM9/ARM11 material. [CITED: GBATEK, “ARM CPU Versions”](https://mgba-emu.github.io/gbatek/#arm-cpu-versions) | Gate decode against ARMv4T. Do not inherit later instructions from the broad chapter; Phase 5 separately pins Tag_CPU_arch v4T and diagnostic cases (ROADMAP.md:202-206). |
| Pipeline-visible PC | The ARM CPU reference describes pipelined fetch/decode/execute and architecture-visible PC offsets: ARM reads use current instruction address +8; Thumb reads use +4. [CITED: GBATEK, “ARM CPU Overview,” instruction summaries](https://mgba-emu.github.io/gbatek/#arm-cpu-overview) | Keep execution address, fetch/pipeline state and operand-visible R15 semantics distinct. Branches/state changes refill the pipeline through bus fetches; no fused/decode-cache path. |
| Banks/modes | ARM7TDMI has User/System shared registers, FIQ's extra banked high registers, and mode-specific SP/LR/SPSR banks; User and System have no SPSR. [CITED: GBATEK, “ARM CPU Register Set”](https://mgba-emu.github.io/gbatek/#arm-cpu-register-set) | Test each mode's bank identity and exception save/return state. Do not model SPSR as one global slot. |
| Exceptions | CPU entry changes mode/state and saves return information in that exception mode; the GBA IRQ vector is 0x18, but the cited BIOS IRQ narrative continues by executing BIOS instructions. [CITED: GBATEK, “ARM CPU Exceptions,” “BIOS Interrupt handling”](https://mgba-emu.github.io/gbatek/#bios-interrupt-handling) | Under BIOS provider none, perform and test architectural exception entry, then stop before fetching/pretending to run a BIOS handler. Keep timer/device IRQ generation out of scope. |
| GBA misalignment | The ARM7/GBA-specific table reports word LDR rotate behavior, odd LDRH as aligned halfword rotated by 8, odd LDRSH as signed-byte behavior, and forced alignment for block transfers. [CITED: GBATEK, “ARM CPU Memory Alignments”](https://mgba-emu.github.io/gbatek/#arm-cpu-memory-alignments) | CPU applies instruction-specific alignment/rotation over raw bus reads. Pin witnesses separately for word, halfword, signed-halfword and LDM/STM. Phase 5 lists these as required diagnostics; treat the GBA quirk claim as a community-reference observation. |
| Open bus / prefetch | GBATEK describes GBA unused-memory reads as recently CPU-prefetched opcode data; ARM and Thumb differ, and Thumb details vary by address region/alignment. Protected BIOS reads return the most recently fetched BIOS opcode. GBATEK warns these results may vary across hardware conditions. [CITED: GBATEK, “GBA Unpredictable Things”](https://mgba-emu.github.io/gbatek/#gba-unpredictable-things) | A single current-data latch is not a general hardware-accurate open-bus model. Preserve explicit latch/pipeline state and CPU fetch through the bus; label chosen read/latch behavior as project policy unless the full region/state behavior is implemented and independently supported. Do not claim BIOS protection while no BIOS provider exists. |
| Cartridge entry and startup stack | GBATEK says the GBA cartridge entry at 0x08000000 contains an ARM branch and reports System mode at entry. It documents BIOS default stacks SP_svc=0x03007FE0, SP_irq=0x03007FA0, SP_usr=0x03007F00, and BIOS IRQ code. [CITED: GBATEK, “GBA Cartridge Header,” “Default memory usage at 03007FXX,” “BIOS Interrupt handling”](https://mgba-emu.github.io/gbatek/#gba-cartridge-header) | These describe cartridge/BIOS conventions, not proof BIOS-none direct start recreated BIOS initialization. Do not present those stack values as actual current hardware state. |

## CP-3: proposed direct-start state (agb, direct-start, BIOS none)

The profile declares boot direct-start and BIOS provider none (profiles/agb.json:2-8); the narrative says execution starts at the cartridge entry without boot ROM execution (docs/profile-agb.md:31-34). Existing initialization policy is exactly memory_fill 0, register_fill 0, master_cycles 0, open_bus 0 (profiles/agb.json:84-90). [VERIFIED: profiles/agb.json:2-8, 84-90; values quoted here.] The narrative explicitly says this policy “does not set Phase 4 CPU direct-start registers” (docs/profile-agb.md:106-111). The table below is a proposed project policy, not an observed GBA post-boot snapshot.

| State | Source-reported fact / confidence | Minimal deterministic project policy to discuss | Unknown or limit |
|---|---|---|---|
| PC / ISA | Cartridge header begins at 0x08000000 with one ARM branch; GBATEK reports System mode at entry. Community reference. [CITED: “GBA Cartridge Header”](https://mgba-emu.github.io/gbatek/#gba-cartridge-header) | Begin executing at 0x08000000 in ARM state; treat the header branch as ordinary guest code. Keep current instruction address separate from visible R15 (+8 ARM / +4 Thumb). | BIOS does not execute or validate the logo; no actual BIOS handoff is reproduced. |
| CPSR | System mode is reported for cartridge entry; exact flags/masks for BIOS-none direct-start are not established by this source. [CITED: “GBA Cartridge Header”](https://mgba-emu.github.io/gbatek/#gba-cartridge-header) | Set System mode, ARM state, clear condition flags, and set IRQ/FIQ mask bits as a conservative deterministic default; guest code may change them. Label this value project policy. | Real post-BIOS flags and mask state are not asserted. Exact initializer is a discussion choice. |
| Shared and banked registers, SP/LR/SPSR | ARM mode banking is architectural; BIOS documentation lists default SVC/IRQ/User stack locations. [CITED: “ARM CPU Register Set,” “Default memory usage at 03007FXX”](https://mgba-emu.github.io/gbatek/#arm-cpu-register-set) | Zero all CPU register banks and SPSRs using the documented deterministic fill convention. Do not install BIOS stack values. Require diagnostic crt0/guest setup to initialize a usable stack. | Intentionally differs from BIOS-initialized state; games requiring BIOS setup are outside this claim. |
| Pipeline | ARM/Thumb PC offsets follow pipeline state. No source establishes what a BIOS-less startup prefetch queue contains. [CITED: “ARM CPU Overview”](https://mgba-emu.github.io/gbatek/#arm-cpu-overview) | Start with an invalid/empty queue and fill by instruction fetches through the bus before executing. Charge these reads under the existing project cycle policy; no hidden startup cycles. | Exact hardware reset/BIOS pipeline contents are not claimed. |
| Master time | Profile initializes master_cycles to 0 under project policy. [VERIFIED: profiles/agb.json:84-90; exact value quoted above.] | Start at zero; every fetch, data access and internal cycle advances through the existing bus clock owner. The profile says each raw request costs one cycle and makes no WAITCNT/prefetch timing claim (profiles/agb.json:66-82). | This does not match hardware timing or qualify throughput. |
| Open-bus latch | Profile initializes it to 0 and calls current-latch reads for absent BIOS, unsupported I/O and ROM tails unverified placeholders (profiles/agb.json:84-99). [VERIFIED: profiles/agb.json:84-99; values quoted above.] GBATEK describes CPU-prefetch-dependent behavior with region/state differences and stability caveats. [CITED: “GBA Unpredictable Things”](https://mgba-emu.github.io/gbatek/#gba-unpredictable-things) | Preserve zero initialization and explicit state; CPU instruction fetches use the bus and update its declared latch behavior. Keep current-latch behavior explicitly project policy. | Do not claim exact hardware open bus, BIOS protection or full Game Pak prefetch. Decide whether Phase 4 adds CPU-fetch coupling only or region/state-specific behavior too. |

The new Phase 4 choice is CPU direct-start state; Phase 3 intentionally left it open. The smallest safe contract is a clearly labeled deterministic start policy with no stack/vector/BIOS claims. Mimicking BIOS stack values or a complete post-boot register snapshot would add claims not established by the selected BIOS-none profile and would imply boot behavior the emulator does not perform.

## Recommended planning and verification witnesses

1. Keep the implementation C17 and dependency-free; add CPU state and executor to the canonical core, with all fetch/data accesses through the bus. Avoid cached/fused host execution because visible PC, bus order, open-bus state and trace are acceptance evidence.
2. Test ARM and Thumb PC visibility (+8/+4), sequential fetch and branch/BX pipeline refill, and explicit latch changes on instruction fetch. Verify cycle changes equal the selected profile policy and state whether startup queue fill counts. Negative cases should show unmapped/absent-BIOS reads follow only declared policy, not an unqualified hardware assertion.
3. Test each mode bank and each exception's mode, banked LR, SPSR, return address and mask/state transition. Exercise IRQ, SWI, undefined and unsupported coprocessor from fresh direct-start state; assert exception state is correct and runner returns named GUEST_STOP before any BIOS-vector fetch.
4. Exercise shifter edge cases (shift >= 32, ROR #0/RRX), signed-overflow helpers, and misaligned LDR/LDRH/LDRSH/LDM/STM under UBSan. Keep ARMv4T-inapplicable opcodes as explicit unsupported instructions, not accidentally accepted ARMv5+ behavior.
5. Headless acceptance should assert one JSON result with separate status, semantic mailbox result, cycle count, claim and limits; peek leaves canonical state/time unchanged; trace category masks and bounded-buffer failure are visible; CLI works after relocation. Use in-memory instructions and owned source-built diagnostics only, never a downloaded/private ROM for CPU unit tests.

Adversarial check: a successful branch at cartridge entry, correct PC offsets, deterministic hashes, or a passing ARM diagnostic does not prove BIOS startup, post-boot registers, instruction timing, prefetch/open-bus accuracy, all hardware revisions or game compatibility. No-BIOS GUEST_STOP is a classified limit, not BIOS emulation.
