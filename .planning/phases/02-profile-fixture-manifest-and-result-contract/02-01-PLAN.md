## User story

**As** the owner/developer, **I want** results and fixtures to have a defined, machine-checked vocabulary (a versioned `agb` profile, a claim tuple on every result, provenance-carrying manifest rows, a SHA-256 pinned fetch, a nine-state result taxonomy, and a dispute registry), **so that** nothing can claim more than its evidence supports. (Framing derived from the ROADMAP Phase 2 goal, which is not written as a user story; same practice as Phase 1.)

cmake/GblJson.cmake (D-01, D-02): first line after the header comment is `cmake_minimum_required(VERSION 3.25)`, then `include_guard(GLOBAL)`. It is both a library and a script-mode entry (same dual-mode guard as cmake/ExpectFail.cmake). Library functions:
- `gbl_json_load(<out-var> <file>)`: the only place that parses a whole file. Steps in order: file absent or not readable prints `json: unreadable: <file>`; file(READ); run `string(JSON <ty> ERROR_VARIABLE <err> TYPE "<text>")` and treat the parse as successful only when `<err>` is exactly `NOTFOUND` or empty (I1: 4.4.3 and 3.25.3 both set `NOTFOUND` on success, probed by the planner; empty is accepted too so a release that clears the variable cannot turn every file into not-json); any other value (including the empty-text and whitespace-only cases) prints `json: not-json: <file>` and never prints the error variable (Pitfall 8: 4.4.3 echoes the input in it, 3.25.3 does not); a root type other than OBJECT prints `json: not-object: <file>`.
- Strictness guard (per D-02, replacing the single trailing-content regex sketched in RESEARCH Pattern 1, which checker issue B1 showed misses a trailing word and a second root because CMake reads the class written for `}` or `]` as `[}\]` followed by a literal `]`). Step 1, strip: replace every string literal with the single letter S using the probed Pattern 1 strip regex. Step 2, comment: when the stripped text contains `//` or `/*`, report `json: comment: <file>` and skip steps 3-5 (they assume comment-free text; a comment may hold brackets or quotes). Step 3, root walk: walk the stripped text one character at a time from index 0 with string(SUBSTRING), adding 1 at each `{` or `[` and subtracting 1 at each `}` or `]`, and stop at the first index where the depth returns to 0; that index is the root's closer. Use only string(SUBSTRING), STREQUAL, and math(EXPR) here; never count brackets with string(REGEX MATCHALL) over a bracket class (the checker saw MATCHALL with such classes under-count on a 1.6 KB document). Step 4, trailing content: the text after the root's closer, with leading space, tab, CR, and LF removed, must be empty; a non-empty rest, or a walk that never returns to depth 0, reports `json: trailing-content: <file>`. Step 5, on the root region only (stripped text from index 0 through the root's closer, or the whole stripped text when the walk never closed), so anything after the root is reported only as trailing-content: report `json: trailing-comma: <file>` when the region matches the probed `,[ \t\r\n]*[]}]`, and `json: duplicate-key: <file>` when the number of string(REGEX MATCHALL) matches of `S[ \t\r\n]*:` in the region differs from the recursive member count of the parsed root from a helper `gbl__json_census(<members-out> <objects-out> <arrays-out> <json>)` (guard every index loop with `LENGTH GREATER 0`, Pitfall 2; recurse only into OBJECT and ARRAY children; the object and array counts are diagnostic outputs kept for the SUMMARY probe note). Planner probe (2026-11-10, CMake 4.4.3 and 3.25.3, identical output): this guard reported only trailing-content for `}`, `,`, `]`, `:`, `;`, a trailing word, and a second root appended to `{"a":1}` and to each of eleven real JSON documents of 223 B to 38 KB (CMakePresets.json, .github/rulesets/main.json, the four RESEARCH example documents, and five planning and tool JSON documents); it accepted all eleven unmodified documents and the tricky clean document; it reported comment, trailing-comma, and duplicate-key (top-level, nested, and duplicate object-valued keys) on their shapes. The executor re-runs these shapes through the json controls; the floor run in plan 07 repeats them on 3.25.3.
- Each loader finding prints with plain `message()`, then the loader ends with `message(FATAL_ERROR "json: failed")` (Pitfall 6).
- Typed accessors, all TYPE-first (Pitfall 3): `gbl_json_type(<out> <json> <key>...)` sets `<out>` to the JSON type or `MISSING` (via ERROR_VARIABLE); `gbl_json_string(<out> <json> <key>...)` sets `<out>` to the value when the type is STRING and the value is non-empty, else to the literal `<missing>`; `gbl_json_length(<out> <json> <key>...)` sets the array length or -1 when the member is not an ARRAY.
- Finding accumulator: `gbl_finding(<family> <code> <detail>)` prints `<family>: <code>: <detail>` with plain message() and increments a GLOBAL property `GBL_FINDINGS`; `gbl_findings_finish(<family> <ok-line>)` prints `<family>: <ok-line>` when the count is 0, else ends with `message(FATAL_ERROR "<family>: failed (<n> findings)")`.
- A file-header comment lists every `json:` reason code, the residual leniencies RESEARCH accepts (leading-zero numbers, raw tabs, BOM), and the rule that callers never iterate JSON text with `foreach(IN LISTS)` and never use `if(<var>)` on JSON-derived strings.
- Script-mode entry: requires `-DFILE=` (missing or empty prints `json: usage: -DFILE= is required` as a fatal), calls gbl_json_load, prints `json: ok: <FILE>`.
Use only the string(JSON) subcommands GET, TYPE, MEMBER, LENGTH, REMOVE, SET, EQUAL.
